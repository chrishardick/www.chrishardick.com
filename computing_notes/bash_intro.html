BASH: An Introduction

What is a shell?

A shell is a text based user interface (UI) for an operating system (Linux, etc.). It allows you to interact with the operating system; e.g. to start and control programs (which could be UNIX utilities, your Python script, your native C or C++ code, or a shell script), access files, etc. Examples of UNIX Shells are: the Bourne Shell, the BASH Shell (Bourne Again Shell), the C Shell, the Korn Shell, etc. The fact that there are many shells is an example of how a UNIX/Linux user can customize their environment. Historically, different shells had different strengths. For example, the Bourne Shell was best for scripting. While the C Shell was better for interactive operation (at the command line). However, with the advancement of shells (i.e. BASH, extended C Shell), this is no longer the case. BASH has become the standard shell across most (if not all) Linux/UNIX flavors

The BASH Shell is an evolutionary successor to the Bourne Shell (hence the Bourne Again Shell); therefore you can execute your existing Bourne Shell scripts using BASH without a loss of functionality or worrying about portability.

Pathname or Wildcard Expansion (Globbing)

When you type a command at the command line. The shell processes the command line before sending the command to the operating system. One thing that happens is Pathname Extension. Pathname Extension takes place when you use wildcards. BASH will expand the wildcards to match filenames (or more generally pathnames). The wildcards which BASH recognizes are as follows:

Wildcard Matches
? Any Single Character
* Any String of Characters (including the NULL string--length 0)
[set] Any character in set
[!set] Any character NOT in set

If you do not want the shell to interpret and expand the wildcards into filenames (or pathnames) shown above, you must quote them--see below. The important thing to realize is that the shell expands the wildcards into filenames and/or pathnames and then passes the expanded string to the indicated command. The command has no idea that the arguments came from the shell and not actual user input.

Standard Input and Output

In the UNIX environment, input and output is treated as a file. Normally, input is read from Standard Input; Output is displayed to Standard Output; and errors are displayed to Standard Error. However since these are all treated as files, they can all be redirected.

For example, you can create a text file to contain the required input for a particular program and redirect the input to come from the file instead of standard input. You can also redirect the output and error streams to external files.

  • The less than sign (<) is used for redirecting standard input
  • the greater than sign (>) is used for redirecting standard output
  • the greater than sign appended with a 2 (2>) is used for redirecting standard error.

This is easy to remember, Standard Error is the 2nd place for output; you can also redirect Standard Output using a greater than sign appended with a 1 (standard output is the 1st or primary place for output).

Some example(s):

  • MyProg <MyProg.in >MyProg.out 2>MyProg.err
  • MyProg <MyProg.in >MyProg.out 2>&1 &

The first example should be pretty easy to figure out. The second example redirects Standard Error (stderr) to same place as Standard Output (stdout); it also run cmd in background--see below.

Pipelines

Pipelines redirect the standard output of one command to the standard input of another command; thereby eliminating the need for temporary files to store intermediate steps of processing. The pipe sign (|) is used for pipelines (or simply pipes). For example:

cut d: -f1 </etc/passwd | sort | lp

parses the file /etc/passwd (a file which contains records of all the users of the system in which the fields are separated by colons and the first field is the user's login name); it sorts the user's login names and then sends its output to the printer. All in one command; and no need to use temporary files.

Background Jobs

Normally when you enter a command at the command line and press ENTER, the command executes and when it's finished, you are returned the prompt.But if you do not feel like waiting around for the program to finish executing before entering another command, you can execute a program in the background. This is specified by placing an ampersand (&) after the command.However if the program requires input; this method should not be used; unless you've provided the input by redirecting the input from a file. Also any output which the program creates (either standard output or standard error) will be displayed on your terminal (mixed in with whatever you're currently doing). If the program creates only a small amount of output, this might be acceptable; however if the program creates a large amount of output, you might want to redirect either standard output, standard error or both so that you are not interrupted.

Quoting Special Characters

As we have seen, there are characters which have special meaning and are interpreted by the shell. For example * (an asterisk) is expanded to any sting (length 0  n) which matches a filename (or pathname).If you do not want these characters to be interpreted to the shell and instead be passed on literally to the program, you must quote them.

There are three methods in which you can use to quote characters with special meaning so that the shell does not interpret them:

  • strong (or single) quoting
  • weak (or double) quoting
  • backslash escaping.

Strong (Single) Quoting

Any string which is surrounded in single quotes is passed in entirety to the specified program without any interpretation by the shell. Therefore single quotes are considered Strong.

Weak (Double) Quoting

Any sting which is surrounded in double quotes is subject to some interpretation by the shell. For example the dollar sign is still interpreted, which means that variables are interpreted--see variables. Also tilde (~) expansion and command substitution is done within double quotes. In bash, the tilde represents a user's home directory so '~/scripts' would be the directory or file named 'scripts' in the current user's home directory; '~john/legal' would expand to the file or directory named 'legal' in john's home directory. Command Substitution (which is discussed later with variables) is when you use the output of a command as the value of a variable; for example Chris=`ls -l 'ch*'` or Chris=$(ls -l 'ch*')--which are alternate forms of the same command, but we'll talk more about this later. Arithmetic Expressions (see Arithmetic discussion) are also evaluated inside of double quotes.

Backslash Escaping

Preceding a character with a backslash has the same effect as surrounding the character in single quotes. Therefore the backslash has special meaning and must be either surrounded in quotes or preceded by a backslash in order not to be interpreted by the shell.

She-Bang Notation

Standard UNIX Scripting Practice is to indicate on the first line of the file, the scripting environment in which to execute the script. This is know as She-Bang Notation, and it is very important. Without it, if you run the C Shell as your standard shell, and you wish to do bash shell programming, you have to do the following at the command line: 

bash FileName
This states that bash should be used to execute your script. The following is an example of she-bang notation. Remember, she-bang notation must be used on the first line of the script; on any other line, it would be interpreted as a comment! With she-bang notation, the shell in which you're in when you execute the script does not matter; bash will always be used to execute your script. 
#!/bin/bash
##  The line above is she-bang notation; if your path to bash is different simply alter the above.

Comments

Comments are portions of your code which are not interpreted by bash. They are provided to help explain your code to other programmers. Use them! Anything on a line following a pound sign (#) is a comment--except the first line.

.bash_profile, .bashrc

  • ~/.bash_profile is executed for login shells
  • ~/.bashrc is executed for interactive non-login shells
  • A standard practice is to source .bashrc from .bash_profile
  • Both files are configuration files - not scripts. Hence you do not need to use she-bang notation, etc.
  • Sample .bash_profile 
    if [ -f $HOME/.bashrc ]; then
    source $HOME/.bashrc
fi
  • Sample .bashrc 
    PATH=$PATH:$HOME/bin
