Transport Layer Protocols (UDP & TCP)



I. UDP

  • User Datagram Protocol
  • Simple transport layer protocol
  • Simple, unreliable, datagram transport level protocol
  • Connectionless
  • Unreliable
    • No guarantee that a UDP datagram will ever reach its destination,
    • No guarantee that the datagrams will arrive in the order sent, or
    • No guarantee that each datagram will be received only once
  • No flow control
  • Basically how it works:
    • Application writes a message to a UDP socket
    • UDP encapsulates the message within a UDP datagram
    • IP encapsulates the UDP datagram within a IP datagram and sends the datagram to its destination


II. TCP

  • Transmission Control Protocol
  • Much more complex transport layer protocol than UDP
  • Sophisticated, reliable byte stream transport level protocol
  • Connection Based
    • A TCP client establishes a connection with a server
    • Data is exchanged back and forth
    • Either side can initiate termination
  • Reliable
    • Each segment (unit of data passed to IP) requires an acknowledgment
    • If the acknowledgment is not received within a specified amount of time, TCP automatically retransmits the data and waits a longer amount of time
    • After a given number of retransmissions, TCP will give up (total time around 4-10 minutes - implementation dependant)
    • TCP uses algorithms to dynamically calculate Round Trip Time (RTT).
    • RTT estimates are used to determine the amount of time to wait for an acknowledgment
    • TCP assigns a sequence number to every byte of data sent
    • Example:
      • Application writes 2K bytes to a TCP socket
      • TCP sends 2 segments to IP - each 1K bytes
      • Segment 1 gets assigned sequence numbers 1-1024
      • Segment 2 gets assigned sequence numbers 1025-2048
      • If the receiving TCP receives the segments out of order, it uses the sequence #'s to deliver the segments to the application in the correct order
      • If the receiving TCP receives duplicate segments, it uses the sequence #'s to discard the duplicate
  • Provides flow control
    • In every segment sent (true???), TCP will tell its peer the exact number of bytes it can accept -- advertised window (the amount of free space in its socket receive buffer).
    • If the socket receive buffer is full, the advertised window will be zero bytes
  • Full-duplex - an application can send and receive data on a given connection at the same time


1. TCP CONNECTION ESTABLISHMENT - 3 WAY HANDSHAKE

  • 3 way handshake because it requires 3 segments: SYN, ACK/SYN, ACK
  • Server prepares a listening socket
  • Client calls connect ( )
    • client TCP sents a SYN (synchronize) segment to client IP
    • SYN segment sent to client IP contains initial sequence number and any TCP options
    • SYN message sent to server contains IP header, TCP header and any TCP options -- THIS IS SEGMENT #1
  • Server acknowledges the SYN (sends an ACK) and sends a SYN of its own.
    • Normally this is sent within the same segment -- THIS IS SEGMENT #2
  • Client acknowledges the SYN (sends an ACK) -- THIS IS SEGMENT #3


2. TCP CONNECTION TERMINATION - 4 SEGMENTS

  • 4 SEGMENTS - FIN, ACK, FIN, ACK
  • Application #1 calls close ( )
    • this is known as an active close -- the 1st application to call close( )
    • TCP sends FIN segment to Application #2 -- THIS IS SEGMENT #1
  • Application #2 receives FIN segment
    • this is known as a passive close -- the application to receive the FIN
    • TCP sends ACK in response to the FIN -- THIS IS SEGMENT #2
    • Since FIN means that the application will not receive any more data, EOF is passed to the application -- read( ) returns 0
    • The TCP connection is now in a half-closed state (Application #2 can still send data)
  • Application #2 calls close ( )
    • TCP sends FIN segment to Application #1 -- THIS IS SEGMENT #3
  • Application #1 receives FIN and responds with ACK -- THIS IS SEGMENT #4


3. TCP CONNECTION STATES

  • These are the states reported by netstat
  • 11 States
  • Some states are only for servers, some states are only for clients
  • TCP rules dictate how clients and servers move from one state to another based upon (1) the current state & (2) the segment received
    1. CLOSED
    2. LISTEN
      • Server only
    3. SYN_SENT
      • Client only. Occurs @ connection establishment when client sends SYN
    4. SYN_RCVD
      • Usually Server. Occurs when in LISTEN state and a SYN is received from a client
    5. ESTABLISHED
      • Client and server. Data transfer state
    6. FIN_WAIT_1
      • The 1st application to call close( ) -- active close. Occurs when in ESTABLISHED state and application calls close( )
    7. FIN_WAIT_2
      • The 1st application to call close( ) -- active close. Occurs when in FIN_WAIT_1 state and ACK is received from peer application
      • Upon FIN_WAIT_2, the 1st application is in a half-closed state
    8. CLOSING
      • Only occurs during a simultaneous close -- not covered
    9. TIME_WAIT
      • Only the 1st applicatin to call close( ) -- active close.
      • Begins when FIN ACK is sent and remains for twice the Maximum Segment Lifetime (2MSL)
      • Maximum Segment Lifetime is usually either 30 seconds or 2 minutes
      • Therefore 2MSL is usually between 1 & 4 minutes
      • The purpose of TIME_WAIT is to guarantee that the socket properly closes
    10. CLOSE_WAIT
      • Only in the 2nd application to call close( ) -- passive close.
      • Occurs when in ESTABLISHED state and a FIN is received
    11. LAST_ACK
      • Only in the 2nd application to call close( ) -- passive close.
      • Occurs when in CLOSE_WAIT state and the 2nd applicaiton calls close( )
