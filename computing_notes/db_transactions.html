Databases: Transactions

I. What's a Transaction?

  • Logical Unit of Work
  • A Unit of Integrity: Not necessarily a single database operation, but rather a sequence of several such operations which, in general, transform the database from one consistent state to another
  • The Unit of Recovery: A transaction can be undone
  • The Unit of Concurrency: A sequence of events which may not be atomic, but can be made to be "pseudo-atomic"

When discussing transactional based processing, there are two main topics:
  1. Recovery
  2. Concurrency


II. Recovery

What's Recovery?
Restoring a database to a valid state after some failure has rendered the current state invalid (or at least suspect)
Commit (Transaction)
Successful End-of-Transaction
Rollback (Transaction)
Unsuccessful End-of-Transaction. The transaction will be undone, in order to insure the database is in a valid state.

III. Concurrency

What's Concurrency?
Concurrency is when multiple applications (or at least multiple processes, or multiple threads) are all accessing the same database, simultaneously. For example, there can be a web application, a UNIX application and a Windows application which all access and update the same database, possibliy stored on another machine (e.g. a database server). These multiple threads (to use the smallest level of granularity) can interfere with one another. In systems where this is unacceptable, some kind of concurrency control mechanism is required.

What problems can occur when concurrency exists?
  1. Lost Update
  2. Duplicate Primary Key
  3. Inconsistent Analysis
  4. Uncommitted Dependency (only applicable when rollback is supported)

Locking: The Standard Mechanism For Dealing With Concurrency

The basic idea: When a transaction (Ta) needs assurance that some DB Object (typically a table row, but could be any db entity - depending on the locking granularity supported) will not change, it acquires a lock on the object. While Ta holds the lock, any other transaction (Tb) which attempts to access the object (via acquiring a lock) will go into a wait state. When Ta is done, it releases the lock & Tb acquires the lock. Locking forces Serializability

Deadlock: Locking Introduces its Own Problem

Deadlock is a situation in which two or more transactions are in a simultaneous wait state, each of them waiting for one of the others to release a lock before it can proceed. I.e. Ta is waiting for Tb to release a lock & Tb is waiting for Ta to release a lock.

Serializability: The Criteron for Correctness for Concurrent Transactions

A given interleaved execution of a set of transactions (Ta, Tb, ..., Tn) is considered correct if it is "serializable." i.e. it produces the same result as some serial execution of the same transactions

PROOF
  • Individual Transactions are "Correct." Remember, transactions transform the database from one valid state to another.
  • Executing a set of transactions (Ta, Tb, ..., Tn) one at a time, in any order, is therefore always correct.
  • An interleaved execution of Ta, Tb, ..., Tn is therefore correct, if it is equivalent to some serial execution of the same transactions.

ACID

ACID is a set of properties database transactions

  • Atomic - a transaction is treated as a single unit which either succeeds or fails
  • Consistency - the database moves from one valid state to another valid state
  • Isolation - currently executing transactions behave as though they were executed in isolation
  • Durability - once a transaction has been committed, it will remain in the database - regardless of a system failure
