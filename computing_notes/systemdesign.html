System Design

This is an assortment of big ticket items to think about when designing a system

Capacity Management

  • Capacity Management can be defined as ensuring a given system has sufficient capacity to handle demands - both expected and unexpected
  • Do you have enough disk space? Enough machines, etc.

Scalability

  • Scalability is defined by wikipedia as the property of a system to handle a growing amount of work by adding resources to the system
  • When talking about computing systems, there are generally two types of scalability - Vertically Scaling and Horizontally Scaling

Vertically Scaling

/ \         +------+
 |          |      | 
 |  +--+    |      |
 |  |  |    |      |
 |  +--+    +------+
  • Vertically Scaling also known as scaling up refers to adding more resources to a given machine. I.e. more CPU, more memory, etc.
  • This could by dynamically (on the fly, not requiring a re-boot) or statically (requiring the machine to be re-booted)
  • Swapping out machines from a less powerful machine to a more powerful machine can also be an example of vertically scaling

Horizontally Scaling

 +--+  +--+  +--+  +--+
 |  |  |  |  |  |  |  |
 +--+  +--+  +--+  +--+

 --------------------->
  • Horizontally Scaling also known as scaling out refers to adding more machines to your pool of resources
  • Scaling horizontally requires you to be able to break up your processing (or part of your processing) such that it can be executed across multiple machines in parallel
  • This could be dynamically (on the fly, not requiring any downtime) or statically (requiring at least some downtime)
  • For example, you could dynamically add more machines to the pool of machines which accomplishes some calculation for you
  • Or you statically reconfigure the data sharding of your system.
  • Your system may be so advanced such that it supports dynamcially reconfiguirng the data sharding

Distributed Systems

  • A distributed system is a computing environment in which components are spread across multiple computers
  • Distributed systems can help with parallelism
  • Distributed systems can also help to reduce single points of failure
  • However, because they're distributed, they usually tend to be more complex and more difficult to observe

Observability

  • I define observability as the ability to measure and monitor the internal state of a system
  • How did your queue size change over time?
  • How did the incoming message rate change over time?
  • How long did it take to process a given message
  • The ability to alarm if your queue size reaches a given high water mark
  • The ability to alarm if your incoming message rate exceeds a certain rate (usually a certain percentage of the time time it takes to process a message)

Debuggability

  • Very important to me, is how easy a system is to debug
  • When things invariably go wrong, how easy is it to figure out what went wrong?
  • Did you design a simple system?
  • Is each piece of the system well documented with a simple picture depicting the flow of data, etc.?
  • Does your system easily inform you when something went wrong?
  • Do errors go to a centralized place making them easy to monitor?
  • Did someone think about what should actually be an error and what actions should be taken if the error is severe enough?

Incident Management (IM) - SLA's, SLO's, SLI's

  • SLA - Service Level Agreement. The promises you make to your customers and the consequences if you fail to meet those promises.
  • SLO - Service Level Objective. These are the individual promises of an SLA. E.g. Percent Uptime, Response Time, etc.
  • SLI - Service Level Indicator. These are the individual measures. I.e. what was the actual uptime, etc.
