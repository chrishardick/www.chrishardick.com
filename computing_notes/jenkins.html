Jenkins

  • Jenkins is one of the most popular CI/CD tools in use today.
  • CI/CD stands for Continuous Integration, Continuous Deployment
  • Jenkins allows you to automate the building, testing, and deployment of software
  • To use Jenkins, you normally create a file named Jenkinsfile which is checked into your version control system.
  • Jenkinsfile defines your Jenkins Pipeline
  • Jenkins Pipelines are typically triggered via a webhook that gets triggered upon commits to a version control system
  • Jenkins Pipelines can also be scheduled via a cron-like system, invoked on demand, etc.

Jenkins Pipeline

  • A Jenkinsfile contains the definition of a Jenkins Pipeline and is checked into source control
  • Jenkins pipelines can be defined using either Declarative Syntax and Scripted Syntax
  • Declarative Syntax is a newer, simpler method to define your Jenkins pipeline.
  • Scripted Syntax is older, more complex, but more powerful.
  • When starting out, it's probably best to start out with Declarative Syntax
  • When using Declarative Syntax, Jenkins Pipelines consist of stages
  • Each stage can be further broken down into a series of steps
  • When using the Declarative Syntax, the source code is automatically checked out for you.

triggers Directive

  • The triggers directive defines an automated way to trigger a pipeline
  • Available triggers are: cron, pullSCM, upstream
  • cron schedules a pipeline at a specified interval
  • pollSCM polls source code management (SCM) at specified interval - uses same syntax as cron 
//
// Field 1: MINUTE (of the hour) (0-59)
// Field 2: HOUR (of the day) (0-23)
// Field 3: DAYOFMONTH (day of the month) (1-31)
// Field 4: MONTH (month of the year) (1-12)
// Field 5: DAYOFWEEK (day of the week) (0-7) where 0 and 7 are Sunday
//

triggers { cron ('*/5 * * * *') }       // every 5 minutes
triggers { cron ('H/5 * * * *') }       // every 5 minutes - spread load evenly

triggers { pollSCM ('*/5 * * * *') }    // every 5 minutes

when Directive

  • when directives control whether a given stage should be executed.
  • The directive must contain at least one condition.
  • If it contains more than one condition, all conditions must be true for the stage to execute 
stage ('blah')
{
    when
    {
        branch 'master'             // execute only for branch=master
        changeRequest()             // current build is for change request (a.k.a. pull request)
        triggeredBy 'TimerTrigger'  // triggered by cron
    }
    steps
    {
        // ...
    }
}

post Build Sections

  • post sections are actions which occur after a single stage or an entire pipeline.
  • post sections allow you to control which actions to take based on the result of a single stage or the whole Pipeline
  • post supports a number of different run conditions. always - always execute; changed - execute when results differ from previous run; success - execute when the stage was successfully completed failure - execute when the stage failed to complete

Comments

  • Irregardless if you're using Declarative Syntax or Scripted Syntax (see below), Jenkins pipelines are Groovy scripts. Hence they support the same types of comments as C++ - namely single and multi-line comments

A Simple Pipeline - Declarative Syntax

// A sample pipeline using declarative syntax
pipeline 
{
    // where to run this pipeline
    agent any

    triggers
    {
        // minute of the day (0-59)
        // hour of the day (0-23)
        // day of month (1-31)
        // month (1-12)
        // day of week (0-7) 0=7=sunday

        // trigger fridays between 6:00 and 6:59
        cron ('H 6 * * 5')
    }

    options 
    {
        // Only keep the 10 most recent builds
        buildDiscarder(logRotator(numToKeepStr:'10'))
    }
    stages 
    {
        stage ('Build') 
        {
            when
            {
                branch 'master'
            }
            steps 
            {
                // build
                sh 'make'
            }
        }
        stage ('Test') 
        {
            steps 
            {
                sh 'make test'
            }
        }
    }
    post 
    {
        always 
        {
            echo "Send notifications for result: ${currentBuild.result}"
        }
    }
}

Declarative vs. Scripted Pipelines

  • Declarative pipelines begin with the keyword pipeline
  • Scripted pipelines begin with the keyword node
  • Declarative pipelines use the stages keyword to define the stages. Each stage is can be further broken down into steps
  • Scripted pipelines contain Groovy code directly in the given stage

Declarative Pipeline

pipeline
{
    agent any

    stages
    {
        stage('Build')  { steps { } }
        stage('Test')   { steps { } }
        stage('Deploy') { steps { } }
    }
}

Scripted Pipeline

node
{
    stage('Build')  { }
    stage('Test')   { }
    stage('Deploy') { }
}
