SOCKET OPTIONS

I. getsockopt( ) / setsockopt( )

    /*
 * getsockopt( )
 * setsockopt( )
 *
 * RETURN
 * ======
 *  0 = success
 * -1 = error (check errno)
 */
#include <sys/socket.h>

int getsockopt (int sockfd,            // in:     open socket descriptor
                int level,             // in:     kernel code which interprets the option: SOL_SOCKET, IPPROTO_IP, IPPROTO_IP6, etc.
                int optname,           // in:     option: SO_ERROR, SO_KEEPALIVE, SO_LINGER, SO_RCVBUF, SO_SNDBUF, SO_RCVLOWAT, SO_SNDLOWAT, etc.
                void* optval,          // out:    current value for the option
                socklen_t* optlen);    // in/out: sizeof(optval)


int setsockopt (int sockfd,            // in:     open socket descriptor
                int level,             // in:     kernel code which interprets the option: SOL_SOCKET, IPPROTO_IP, IPPROTO_IP6, etc.
                int optname,           // in:     option: SO_ERROR, SO_KEEPALIVE, SO_LINGER, SO_RCVBUF, SO_SNDBUF, SO_RCVLOWAT, SO_SNDLOWAT, etc.
                const void* optval,    // in:     new value for the option
                socklen_t optlen);     // in:     sizeof(optval)
  • Level: what level of kernel code should interpret the option
    • SOL_SOCKET: general socket code
    • Protocol specific code
      • IPPROTO_IP - IPv4 protocol specific code
      • IPPROTO_IP6 - IPv6 protocol specific code
      • etc.
  • Four types of options:
    1. Flag options (either on or off)
      • optval is an integer
      • non-zero = true (on)
      • zero = false (off)
    2. Integer options
      • optval is an integer
    3. timeval options
      • optval is a timeval struct
    4. linger option
      • optval is a linger struct

1. GENERIC SOCKET OPTIONS

  • protoocl independent - handled by protocol independent code within the kernel
  • level = SOL_SOCKET (general socket code)

SO_BROADCAST Socket Option

  • Option Type: Flag
  • Enable/disable the ability of the process to send broadcast messages
  • Broadcasting is supported only for datagram based sockets (not connection based sockets) and only on networks that support the concept of a broadcast message (ethernet, token ring, etc.)

SO_DEBUG Socket Option

  • Option Type: Flag
  • Only supported by TCP
  • When enabled, the kernel keeps track of detailed information about the packets sent and received by TCP for the socket
  • These can be viewed with the trpt program

SO_DONTROUTE Socket Option

  • Option Type: Flag

SO_ERROR Socket Option

  • Option Type: Int
  • Cannot be set by setsockopt( )

SO_KEEPALIVE Socket Option

  • Option Type: Flag
  • Connection based sockets only (not sure if only TCP, might also be SCTP)
  • Purpose: detect if peer host crashes or becomes unreachable
  • Normally used by servers
  • Behavior when set: if no data has been exchanged for 2 hours, TCP will automatically send a probe
  • Probe is a TCP segment in which the peer is required to acknowledge (like any other TCP segment)
  • If peer responds with the requird ACK, the application will not be notified
  • If peer responds with RST (the peer host has crashed and rebooted) and socket's pending error is set to ECONNRESET and socket is closed
  • If peer does not respond within the timeout interval (implementation dependant), additional probes will be sent. If still no repsonse, the socket's pending error is set to ETIMEDOUT and the socket is closed. Berkeley derived implementations send 8 additional probes, 75 seconds apart

SO_LINGER Socket Options

  • Option Type: linger
  • See also close( ), shutdown( ) 
    struct linger
{
     int l_onoff;       // 0=off, non-zero=on 
     int l_linger;      // linger time (secs)
};
  • Controls how close( ) behaves for connection based protocols
  • By default (LINGER OFF), close( ) returns immediately and the application has no way of knowing
    1. if the peer TCP has received and acknowledged the data
    2. if the peer application has read and processed the data
  • By turning LINGER ON and specifying a linger timeout value, close( ) will not return until either (1) linger timeout value has expired, or (2) the peer TCP has acknowledged the data. Therefore, by specifying an appropriate timeout value, the application can be assured that the peer TCP has received the data
  • In order for the application to know that the peer application has read and processed the data, shutdown(SHUT_WR), followed by read( ) must be utilized
  • If LINGER ON is specified, but the timeout value is set to 0 (zero), TCP will abort the connection immediately (any data in the socket send buffer is discarded) and RST (reset) is sent to the peer. I'm not sure when this is useful.

SO_RCVBUF/SO_SNDBUF Socket Options

  • Option Type: Int
  • Every socket has a socket send buffer and a socket receive buffer
  • Allows you to change the default sizes
  • TCP buffer sizes for connected sockets are always inherited from the listening socket
  • Socket Receive Buffer
    • For TCP, the available size in the receive buffer is the advertised window which is advertised to the TCP peer. This is TCP's flow control.
    • With both TCP and UDP, if a segment arrives which will not fit in the socket receive buffer, it will be discarded
    • For TCP clients, this option must be set prior to calling connect( )
    • For TCP servers, this option must be set for the listening socket, prior to calling listen( )
  • Socket Send Buffer
    • UDP does not physically have a socket send buffer--it's not a reliable protocol and need not keep a copy of the data for re-transmission. For UDP, SO_SNDBUF is simply an upper bound on the maximum sized UDP datagram which can be written to the socket (not the size of a physical buffer)

SO_RCVLOWAT/SO_SNDLOWAT Socket Options

  • Option Type: Int
  • Every socket has a receive low water mark and a send low water mark
  • These options are used by select( )
  • Receive low water mark
    • Amount of data (bytes) which must be present in the socket receive buffer in order for select( ) to return 'readable'
    • Usually defaults to 1 for UDP, TCP, and SCTP
  • Send low water mark
    • Amount of free space (bytes) which must be available in the socket send buffer in order for select( ) to return 'writable'
    • Usually defaults to 2048 for TCP sockets
    • For UDP sockets, which do not really have socket send buffers, as long as the send low water mark is less than the size of the socket send buffer (not an actual buffer), the socket is always 'writable'

SO_RCVTIMEO/SO_SNDTIMEO Socket Options

  • Option Type: timeval 
    struct timeval
{
     long tv_sec;
     long tv_usec;
};
  • allows you to place a timeout on socket sends and receives
  • both timeouts are disabled by default
  • send timeouts affect the following functions:
    • write( )
    • writev( )
    • send( )
    • sendto( )
    • sendmsg( )
  • receive timeouts affect the following functions:
    • read( )
    • readv( )
    • recv( )
    • recvfrom( )
    • recvmsg( )

SO_REUSEADDR Socket Option

  • Option Type: Flag
  • All TCP Servers should specify this option
  • This option has several different purposes
    1. Allows a listening socket to bind to its well-known port, even if other socket(s) currently exist which are the port as their local port. This usually occurs as follows:
      • A listening server is started
      • A connection request arrives and a child process is spawned
      • The listening server terminates (child continues executing)
      • Listening server is restarted
        • Under default conditions (SO_REUSEADDR is off), bind( ) would fail - port already in use
        • Unless the listening socket sets the SO_REUSEADDR option prior to calling bind( )
    2. Allows a new server to be started on the same port as an existing server so long as each server binds to different local IP address (including the wildcard address)
      • Frequently used to allow for different servers to service different IP addressses (i.e. a HTTP server)
      • Assume we have a server with 5 IP addresses (1,2,3,4,5)
      • Server #1 starts up and binds to port 80 w/ IP address #1
      • Server #2 starts up and binds to port 80 w/ IP address #2
      • Server #3 starts up and binds to port 80 w/ IP wildcard address
      • Server #1 will service all requests on address #1
      • Server #2 will service all requests on address #2
      • Server #3 will service all requests on address' #3, 4 and 5
      • The wildcard address is better defined as "every address that does not have a better match"
      • Note: even with SO_REUSEADDR specified, you can never bind to the same address with the same port (completely duplicate binding)
    3. SO_REUSEADDR also has 2 other purposes which are usually only used for UDP sockets

SO_REUSEPORT Socket Options
