Linux - systemd

  • systemd is a system and service manager for Linux.
  • It is currently the default system and service manager for most Linux distributions.
  • Developed by RedHat
  • Some people believe the scope of systemd is too large and runs contrary to the Unix philosophy of small interconnected utilities with narrowly defined functionality. These people would like to see systemd displaced.
  • Items managed by systemd are known as units
  • Units can be services (similar to other init systems -- and the most popular type of units). They can also be other objects (sockets, devices, a filesystem mount or activity, etc.)

Quick Start

This quick start will show you how to quickly create a service which auto-starts at boot time

  • Create a Unit Configuration File (e.g. hello_world.service) 
    [Unit]
Description     = Hello, World! service

[Service]
ExecStart       = /user2/python/hello_world.py

[Install]
WantedBy        = multi-user.target
  • Install your Unit Configuration File to /etc/systemd/system/
  • systemctl start hello_world.service
    • This will attempt to start up your service
  • systemctl enable hello_world.service
    • This will enable your service to automatically start at boot time (creates a sylink under /etc/systemd/system/multi-user.target.wants/)

Unit Types

  • There are 12 types (categories) of systemd units
  • Each unit type has a unique suffix. For example, a .service suffix indicates a service (the default and most common type of unit).

Here is a list of all unit types:

  • Service Units
    • Start and control daemons along with any related processes
    • suffix: .service
    • For more information: man systemd.service
  • Socket Units
    • suffix: .socket
    • For more informaation: man systemd.socket
  • Target Units
    • useful to group units or provide well-known synchronization points during boot up. Similar to run levels in init.
    • suffix: .target
    • For more information: man systemd.target
  • Device Units
    • suffix: .device
    • For more information: man systemd.device
  • Mount Units
    • suffix: mount.
    • For more information: man systemd.mount
  • Automount Units
    • suffix: .automount
    • For more information: man systemd.automount
  • Snapshot Units
    • suffix: .snapshot
    • For more information: man systemd.snapshot
  • Timer Units
    • suffix: .timer
    • For more information: man systemd.timer
  • Swap Units
    • suffix: .swap
    • For more information: man systemd.swap
  • Path Units
    • A unit can be started based on the activity or availability of a filesystem path (via utilizing inotify)
    • suffix: .path
    • For more information: man systemd.path
  • Slice Units
    • suffix: .slice
    • For more information: man systemd.slice
  • Scope Units
    • suffix: .scope
    • For more information: man systemd.scope

systemctl

The systemctl command allows you to control systemd.

systemctl start application[.service]
start a systemd service.
systemctl stop application[.service]
stop a systemd service.
systemctl restart application[.service]
restart (bounce) a systemd service.
systemctl status application[.service]
check the status of a systemd service
systemctl enable application[.service]
to configure a systemd service to automatically start at boot time (creates a symlink)
systemctl disable application[.service]
to configure a systemd service to no longer automatically start at boot (removes a symlink)
systemctl [--all]
list all running services
use the --all switch to list unts -- not just the currently active (executing) ones
systemctl status
show system status
systemctl --failed
list failed units
systemctl list-unit-files --type=service
display the status of all installed services
enabled - will start at boot
disabled - will not start at boot
static - means the service is missing the [Install] section in its init script, so you cannot enable or disable it. Static services are usually dependencies of other services and are controlled automatically
systemctl reload application[.service]
have a systemd service reload its configuration (if supported)
systemctl is-active application[.service]
check if a given systemd service is currently executing (will return a 0 exit code if active)
systemctl is-enabled application[.service]
check if a given systemd service is enabled (i.e. configured to automatically start at boot time) - will return a 0 exit code if enabled
systemctl is-failed application[.service]
check if a given systemd service is in a failed state (i.e. there was an error starting it) -- will return a 0 exit code if in failed state
systemctl list-dependencies [--all] application[.service].
to show dependencies for the given service
to expand dependent units recursively, pass the --all flag
these are the services which systemd will attempt to activate when starting the unit
use the --reverse flag to see what is dependent on a given application
use the --before flag to show applications which depend on the specified application starting before them (the --after flag is similar)
systemctl cat application[.service]
to see the contents of a unit file
systemctl mask application[.service]
mask an application (make it unstartable -- either automatically or manually -- by linking it to /dev/null)
use unmask to unmask it
systemctl get-default
to view the default target which will be used at boot time
systemctl set-default <target>
to view the default target which will be used at boot time
E.g. systemctl set-default multi-user.target
systemctl poweroff
systemctl reboot
systemctl rescue

Unit Files

An example (/etc/systemd/system/kidsnet_monitor_devices.service):

[Unit]
Description     = kidsnet - keep device table up-to-date

[Service]
ExecStart       = /user2/kidsnet/kidsnet_monitor_dhcp.sh

[Install]
WantedBy        = multi-user.target

Sections

  • The contents of unit files are organized into Sections
  • Sections are denoted via a section name enclosed in square brackets ([...])
  • A Section continues until the beginning of the next section or EOF
  • Section names are well defined and case-sensitive
  • Each section has directives which have the form directiveN=value
  • You can leave a directive unset by not assigning a value. E.g. directiveN=

[Unit] Section

The Unit Section has the following directives:

Description=
Defines the name and basic functionality of the unit.
It is returned by various systemd tools.
Documentation=
List of URI's for documentation.
Ususally either man pages or web URL's
It is returned by various systemd tools.
Requires=
An example: unit1.service contains Requires=unit2.service
Lists any units upon which this unit depends (e.g. unit1.service dspends on unit2.service)
In other words, if unit2.service does not successfully start, unit1.service will also be deactivated
Note: this has nothing to do with the order in which the services are brought up
By default, these units (unit1.service and unit2.service) are started concurrently
Wants=
An example: unit1.service contains Wants=unit2.service
Similar to Requires, but the service will not be deactivated if any dependent services fail to start
In our example, unit1.service will not be deactivated if unit2.service fails
BindsTo=
Similar to Requires, but also causes the current unit to stop when these unit(s) terminate
Before=
An example: unit1.service contains Before=unit2.service
Deals with unit start-up order
In our example, unit1.service will be executed fully before unit2.service starts
The units listed here will not be started until the corrent unit is marked as started if they are activated at the same time
After=
Deals with unit start-up order
The units here will be started before starting the current unit
Conflicts=
The units here cannot be run at the same time as the current unit.
Starting a unit in the list will cause the other units to be stopped

[Service] Section

  • applicable to service units ONLY.

The Service Section has the following directives:

Type=
The Type directive can have one of the following values
  • simple - default type
  • forking - used when the service forks a child process exiting the parent process.
  • oneshot - a short-lived process. systemd shoudl wait for the process to exit before continuing with other units
  • dbus - indicates that the unit will take a name on the D-Bus bus.
  • notify - indicates that the unit will issue a notification when it has finished starting up. systemd will wait for this before continuing with other units.
  • idle - indicates that the service will not be run until all jobs are dispatched.
ExecStart=
The full path and arguments of the command to be executed.
If the path is preceeded by a dash (-), non-zero exit statuses will not mark the unit activation (i.e. currently running) as failed
ExecStartPre=
This can be used to provide additional commands to be executed before the main process
This directive is optional and can appear multiple times
Full paths must be specified
Dash prefix is supported
ExecStartPost=
This can be used to provide additional commands to be executed after the main process
This directive is optional and can appear multiple times
Full paths must be specified
Dash prefix is supported
ExecReload=
The command to reload the service configuration -- if supported
This directive is optional
Full paths must be specified
ExecStop=
The command to stop the service.
If not specified, the process will be killed when the service is stopped
ExecStopPost=
Optional directive used to specify commands to execute following the stop command
Restart
Optional directive used to indicate when systemd shoudl attempt to automatically restart the service
  • always
  • on-success
  • on-failure
  • on-abnormal
  • on-abort
  • on-watchdog
  • E.g. Restart=always - enable the service to respawn
RestartSec=
If automatically restarting the service is enabled, this is the amount of time to wait before attempting to restart the service

[Install] Section

  • The last section. It is optional.
  • Used to define if a unit is enabled (automatically started at boot-time) or disabled (not automatically started at boot-time)
  • Usually this accomplished by associating the unit with another unit that is currently started at boot

The Install Section has the following directives:

WantedBy=
The most common way to specify that a unit should be enabled
When a unit with this directive is enabled, a symbolic link to the unit named <unit-name>.wants will be added under the /etc/systemd/system/<wanted-by-unit> directory (e.g. /etc/systemd/system/multi-user.target.wants). The directory will be created if it did not already exist.
RequiredBy=
Similar to the WantedBy= directive, but specifies a required dependency
Instead of the .wants subdirectory, this directive uses a .requires subdirectory (e.g. /etc/systemdsystem/multi-user.target.requires)
Alias=
Allows the unit to be enabled under another name
Also=
Allows units to enabled or disabled as a set.
DefaultInstance=
Used for template units to give them more predictable names

Unit File Directories

/lib/systemd/system
The system's copy of the unit files
Generic, vanilla files.
You should not edit files in this directory. Instead, you should override the file by placing another unit file directory which will supersede the files in this directory
/etc/systemd/system
Unit files in this directory take precedence over unit files in any other location
If you need to override only specific directives from a system unit file (in /lib/systemd/system), you can do so via subdirectories to this directory
Can contain sub-directories with .wants symbolic links (see above)
/run/systemd/system
