PTHREADS: THREAD CANCELLATION


  • a facility which allows you to tell a thread to shut itself down


1. PTHREAD_CANCEL( ): REQUEST TO CANCEL A THREAD

  • In order to request to cancel a thread, you must have the thread's identifier (pthread_t)
  • pthread_cancel( ) is an asynchronous function, it returns immediately. When pthread_cancel( ) returns, the thread may or may not have been cancelled
  • If you need a cancellation request to be synchronous, you must join with it, by calling pthread_join ( ).
  • If the thread's cancellation mode is deferred, the cancel request will be delivered when the thread reaches its next cancellation point
  • If the thread's cancellation mode is asynchronous, the cancel request will be delivered immediately
  • If the thread's cancellation mode is off, the cancel request will not be sent until cancellation is enabled (either deferred or asynchronous)
  • When a cancel request is being processed, the system will set the thread's cancellation mode to off, such that the thread can clean itself up without worrying about handling another cancel event 
    #include <pthread.h>

/*
 * request to cancel a thread
 *
 * RETURN
 * ======
 * 0 = success
 * else - see discussion on pthreads and errors
 * 
 */
int pthread_cancel(pthread_t thread);

3. DEFERRED CANCELABILITY (TYPE=DEFERRED, STATE=ENABLED)

  • TYPE = PTHREAD_CANCEL_DEFERRED
  • STATE = PTHREAD_CANCEL_ENABLE
  • the thread will only respond to cancellation requests when it reaches a cancellation point
  • cancellation points are the only functions which respond to cancel requests under deferred cancelability
  • check your system documentation for a complete list of cancellation points
  • the general rule is that all blocking functions are usually cancellation points
  • when a thread reaches a cancellation point, the system checks for pending cancel message(s)
    • if a cancel is pending, the system will call all cleanup functions (see section below) & terminate the thread
    • if no cancel is pending, the function will proceed as normal
    • while the cancellation point is executing, if a cancellation requst comes in while the function is blocked, the wait will be interrupted and cleanup functions will be called
  • If you need to prevent cancellation during any cancellation point, you need to temporarily disable cancelability

4. ASYNCHRONOUS CANCELABILITY (TYPE=ASYNCHRONOUS, STATE=ENABLED)

  • TYPE = PTHREAD_CANCEL_ASYNCHRONOUS
  • STATE = PTHREAD_CANCEL_ENABLE
  • useful to interrupt computation intensive operations
  • avoid asynchronous cancelability at all costs -- it's dangerous
  • if you must, be sure to call no code while asynchronous cancellation is enabled unless it's async-cancel safe
  • check man pages to determine if a function you want to call is async-cancel safe. If the man page does not state whether or not it is async-cancel safe -- assume the function is not.
  • while asynchronous cancellation is enabled, you cannot acquire any system resources
  • Cleanup handlers are still called, but other functions you call (which are not async-cancel safe), will not be able to clean up after themselves
  • Deferred cancelability is safer because it only allows cancellation at specified points.

5. CLEANUP

  • the complexity of thread cancellation is that a thread may be cancelled while it holds on to system resources (i.e. dynamically allocated memory, a mutex lock, etc.) which must be properly released. As further complication, before unlocking the mutex, the system must be returned to a valid state. I.e. if your mutex controls a list consisting of an array of items & a counter of how many items on the list, when you unlock the mutex, you have ensure a valid list
  • each thread may have a stack of active cleanup handlers
  • cleanup handlers are added to the stack by calling pthread_cleanup_push()
  • the most recently added cleanup handler is removed (poped) from the stack by calling pthread_cleanup_pop()
  • you cannot push a cleanup handler in one function and pop it in another function.
  • IMPORTANT: pthread_cleanup_push() & ptherad_cleanup_pop(), may be defined as macros, and as such, matching calls must always be called within the same function
